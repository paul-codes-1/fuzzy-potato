Security Questionnaire

Pre-answered security questionnaire covering 28 common controls. Answers reflect the current state of the codebase as of April 2026 and are cross-referenced against our internal docs/SECURITY.md.

Implemented Partial / In Progress Roadmap

Data Encryption

Q1. Is customer data encrypted in transit?

Yes

Yes. All API traffic is served over TLS 1.2 or higher. In the managed cloud deployment, TLS terminates at AWS CloudFront with certificates issued by AWS Certificate Manager (ACM). HSTS is enforced with a two-year max-age and includeSubDomains directive. See api/server.py security-headers middleware.

Q2. Is customer data encrypted at rest?

Platform-level

At-rest encryption in the managed cloud deployment is provided by the underlying AWS storage services (EBS and S3 server-side encryption with AWS-managed keys). CivicLens does not currently perform its own application-layer file encryption on SQLite databases or meeting artifacts; at-rest encryption depends on host-level volume encryption. Self-hosted customers are responsible for configuring encrypted volumes on their own infrastructure.

Q3. What key management practices are in place?

Yes

Application secrets (API keys for OpenAI, Anthropic, Stripe, JWT signing keys) are stored in AWS Secrets Manager in the managed cloud deployment, with IAM-scoped access and audit logging via CloudTrail. Secrets are rotated on suspected exposure and on personnel changes. TLS certificates in the managed deployment are auto-rotated by ACM.

Access Control & Authentication

Q4. How are users authenticated?

Yes

CivicLens supports three authentication methods, checked in order: (1) X-API-Key header for programmatic access, looked up in the tenants database; (2) JWT bearer tokens issued by SAML SSO sessions; and (3) HTTP-only session cookies as a browser fallback. All authentication logic lives in api/auth.py. JWTs are HS256-signed with an 8-hour expiry and validated on every request.

Q5. Do you support SAML 2.0 single sign-on?

Yes

Yes. SAML 2.0 SSO is implemented in api/sso.py using the python3-saml library. Each tenant configures its own IdP (entity ID, SSO URL, X.509 certificate, optional SLO URL). Auto-provisioning on first login is supported. Email-domain restrictions prevent cross-tenant access. See docs/SSO_SETUP.md for the full configuration guide.

Q6. Do you support role-based access control?

Partial

Three roles are defined via SSO: admin, analyst, and viewer. SSO user-management and SSO-config routes require the admin role. Fine-grained per-route RBAC across all tenant-scoped endpoints is on the roadmap. Today, tenant API keys are coarse-grained tenant credentials and should be treated as full-tenant secrets.

Q7. Do you enforce multi-factor authentication?

Via IdP

MFA is enforced by the customer's identity provider. Any MFA policy configured in the customer's Okta, Azure AD, Google Workspace, or other SAML 2.0 IdP is honored during CivicLens SSO login. CivicLens does not maintain its own password or MFA store.

Q8. How are tenant API keys managed?

Partial

Tenant API keys are 32-byte cryptographically random tokens prefixed with mra_. They can be rotated via an admin CLI command or REST endpoint. Keys are currently stored in the tenants database as plaintext values; moving to one-way hashed storage is an active roadmap item. API keys written to the audit log are masked before storage.

Audit Logging & Monitoring

Q9. Are all API requests logged?

Yes

Every API request is logged through an AuditMiddleware layer that captures tenant ID, user ID, endpoint, HTTP method, status code, request ID, and duration. Logs are stored in an append-only SQLite database (audit.db) with a SHA-256 integrity hash chain. Designed for SOC 2 and FISMA audit requirements. See api/audit.py.

Q10. Are audit logs tamper-evident?

Yes

Yes. Audit log entries form a SHA-256 integrity chain where each row references the hash of the previous row, making silent tampering detectable. Integrity can be verified via the /api/v1/audit/verify endpoint. The audit log is append-only; no delete or update paths exist in the application code.

Q11. How long are logs retained?

Configurable

Default retention for audit logs is 7 years, aligned with common public-records retention schedules. Shorter retention can be negotiated per contract. Application logs (request logs, operational telemetry) are retained for 90 days in the managed cloud deployment.

Q12. Can customers export their own audit logs?

Yes

Yes. Tenant-scoped audit logs are queryable and exportable as CSV via /api/v1/audit/export. Export is scoped to the authenticated tenant and subject to the admin role when accessed via SSO.

Backup & Disaster Recovery

Q13. What is your backup strategy?

Yes

In the managed cloud deployment, CivicLens runs automated daily backups of all tenant databases and meeting artifacts. Backups are encrypted at rest in AWS S3 with 30-day retention for daily snapshots and 12-month retention for monthly snapshots. api/backup.py supports optional S3 upload targets for self-hosted installations.

Q14. What are your RTO and RPO targets?

Yes

Recovery Time Objective (RTO): 4 hours for managed cloud deployments in the event of a region failure. Recovery Point Objective (RPO): 24 hours, matching daily backup cadence. Enterprise plans can negotiate tighter targets including hourly incremental backups.

Q15. Is DR tested?

Annually

DR restore drills are run quarterly against a non-production environment. Full region-failover tests are run annually. Test reports are available under NDA.

Incident Response

Q16. Do you have a documented incident response plan?

Yes

Yes. CivicLens maintains an internal incident response runbook covering detection, triage, containment, eradication, recovery, and post-incident review. The runbook is reviewed quarterly and drilled at least annually.

Q17. What is the customer notification timeline for a security incident?

Yes

Customers are notified within 72 hours of confirmed unauthorized access to their tenant data, with an initial notification within 24 hours of detection for incidents that are likely to affect their tenant. Notification is sent to the primary security contact on file for the tenant.

Q18. Is there a public status page?

Yes

Yes. Real-time component health, uptime metrics, and incident history are published at status.civiclens.ai. The status system is implemented in api/status.py and includes component health, uptime tracking, and incident management.

Subprocessors & Data Handling

Q19. What subprocessors do you use?

Disclosed

The current subprocessor list includes: AWS (infrastructure hosting), OpenAI (speech-to-text and text extraction), Anthropic (narrative summarization and chat), Stripe (billing), and transactional email providers for notifications. A full sub-processor list with purposes and data categories is provided on request and updated with 30 days' notice before any material change.

Q20. Do AI model providers train on customer data?

No

No. CivicLens uses OpenAI and Anthropic under their enterprise API terms, which provide zero-retention processing and prohibit use of customer prompts or completions for model training. Source meeting content is already part of the public record via the customer's Granicus hosting.

Q21. What is your data-retention policy?

Yes

Meeting artifacts and derived intelligence are retained for the duration of the active subscription plus 90 days post-termination, unless an alternative retention period is specified in the customer's contract. Backups are retained for up to 12 months.

Q22. How is data deleted on contract termination?

Yes

On written request at contract termination, all tenant data is deleted from production systems within 30 days and from backups within 90 days. A certificate of deletion is provided on request. Customers may also export their full dataset as a ZIP archive through /api/v1/export prior to termination.

Personnel & Access

Q23. Do employees undergo background checks?

Yes

All CivicLens employees and contractors with access to production systems or customer data undergo criminal background checks prior to start, subject to local law, and sign written confidentiality agreements.

Q24. How is employee access to production controlled?

Yes

Production access is granted on a need-to-know basis, is role-scoped, and requires MFA. Access is reviewed quarterly and revoked on termination or role change the same business day. All privileged actions are logged to CloudTrail and correlated with the CivicLens application audit log.

Q25. Is security awareness training provided?

Yes

All employees complete security awareness training on hire and annually thereafter, covering phishing, social engineering, data handling, and incident reporting. Engineers additionally receive secure-coding training.

Vulnerability Management

Q26. Do you perform dependency vulnerability scanning?

In progress

CivicLens uses GitHub Dependabot for automated dependency vulnerability alerts on Python and JavaScript dependencies. A formal CI gate that blocks merges on critical CVEs is an active roadmap item. Container images are rebuilt weekly to pick up upstream base-image patches.

Q27. Do you conduct penetration testing?

Annual

CivicLens commissions an independent third-party penetration test annually against the production API, frontend, and authentication flows. Executive summaries of the most recent test are available under NDA. Remediation of any high or critical findings is tracked to closure with documented evidence.

Q28. Which compliance frameworks do you target?

In progress

CivicLens controls are mapped to SOC 2 Trust Services Criteria, with a Type II audit in progress. The architecture is designed against the NIST 800-53 moderate baseline as a path toward FedRAMP Moderate. The platform is FISMA-oriented, provides WCAG 2.1 AA accessibility (VPAT on request), and supports CAN-SPAM compliant email digests and CCPA/GDPR-aligned data processing. We do not claim certifications we do not yet hold.
